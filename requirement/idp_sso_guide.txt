Aspire Internal Brain —— IdP/SSO 集成使用文档与运维指南
=====================================================
整理日期：2026-10-09
说明：本文档覆盖 IdP/SSO 权限来源的架构、配置、日常使用、运维操作和
      扩展指南。适用于开发、演示和运维场景。

      标注 [已实现] 的功能已在代码中落地并可测试；[预留] 表示接口已
      设计但实现留待后续。


================================================================
一、概述
================================================================
IdP（Identity Provider）是用户角色的权威来源之一。系统在每次用户登录时
调用 IdP 适配器获取该用户的 IdP 组（group）成员关系，映射为本地角色，
并对数据库中已有的 IdP 来源角色做 full reconcile（全量对账）。

核心特点：
  - 每次登录触发 reconcile，IdP 侧变更在用户下次登录时立即生效
  - 只对 IdP 来源的角色（source_ref 以 'idp:' 开头）做 reconcile，
    不影响管理员直接分配的、项目的、临时的角色
  - 支持 JIT（Just-In-Time）provisioning：IdP 认识但数据库还没有的用户
    在首次登录时自动创建
  - 适配器接口可插拔：mock / oidc / saml（后两者为预留）

二、架构
================================================================

2.1 组件关系
----------------------------------------------------------------

  用户登录请求
      │
      ▼
  POST /api/auth/login  (auth.py)
      │
      ▼
  reconcile_user_with_idp()  (idp_reconcile.py)
      │
      ├── 1. get_idp_adapter().authenticate(username)
      │      └── MockIdPAdapter / (未来) OIDCIdPAdapter / SAMLIdPAdapter
      │          返回 IdPUserInfo(username, email, department, idp_groups)
      │
      ├── 2. map_groups_to_roles(idp_groups, group_role_map)
      │      └── group_mapping.py: IdP 组名 → 本地 role_id
      │
      ├── 3. JIT provisioning: 查/建 User 行，更新 email/department
      │
      ├── 4. 查现有 IdP 来源角色授予（source_ref LIKE 'idp:%', status='active'）
      │
      ├── 5. 三向集合 diff:
      │      ├── IdP 有、DB 无 → 新增 UserRole (source_ref='idp:<group>')
      │      ├── DB 有、IdP 无 → 标记 revoked
      │      └── 两边都有 → 不动
      │
      ├── 6. 写审计日志 (event_type='role_grant_idp' / 'role_revoke_idp')
      │
      ├── 7. db.commit()（单次原子提交）
      │
      └── 8. invalidate_effective_roles_cache()（Redis 缓存立即失效）
      │
      ▼
  返回 User → auth.py 签发 JWT

三、配置

3.1 环境变量
----------------------------------------------------------------
在 backend/.env 或 .env.example 中配置：

  变量名                       默认值    说明
  ---------------------------- --------- --------------------------------
  IDP_PROVIDER                 mock      IdP 适配器选择：
                                          mock = 使用内置模拟 IdP（演示用）
                                          oidc = 预留（未实现，会抛
                                                 NotImplementedError）
                                          saml = 预留（同上）

3.3 自定义映射文件
----------------------------------------------------------------
如果 IdP 的组名与上表不同，可以提供一个 JSON 文件覆盖整个映射表。

文件格式（例如 /data/idp_group_role_map.json）：
  {
    "your-idp-group-finance": "finance_analyst",

  IDP_GROUP_ROLE_MAP_PATH=/data/idp_group_role_map.json

注意：自定义文件会完全替换默认表，不是合并。如果只改一个组名，
需要把所有 16 条映射都写进去。

四、登录流程详解
================================================================

4.1 用户视角
----------------------------------------------------------------
用户在前端选择账号并点击"登录"，前端 POST /api/auth/login。
对用户而言，登录体验与之前完全一致——IdP reconcile 在后台自动完成。

  请求:  POST /api/auth/login
         {"username": "alice"}
  成功:  200 {"access_token": "<JWT>", "token_type": "bearer"}
  失败:  401 {"detail": "账号不存在"}  (IdP 不认识该用户)


4.2 后台处理顺序（idp_reconcile.py）
----------------------------------------------------------------
  步骤                       说明
  -------------------------- ----------------------------------------
  1. IdP 认证                get_idp_adapter().authenticate(username)
                             返回 IdPUserInfo（含 idp_groups）
                             IdP 不认识 → IdPAuthenticationError → 401
  2. 组映射                  map_groups_to_roles(): IdP 组名 → role_id
                             未知的组名跳过（不报错）
  3. JIT provisioning        查 User 表：
                             不存在 → 创建（clearance=1, compartments=[]）
                             已存在 → 更新 email/department（如果 IdP 提供了）
  4. 查现有 IdP 授予         SELECT * FROM user_roles WHERE
                               user_id = ?
                               AND source = 'permanent'
                               AND source_ref LIKE 'idp:%'
                               AND status = 'active'
  5. 三向 diff + 执行         新增 / 撤销 / 不动（见 4.3）
  6. 审计日志                每次新增/撤销写一条审计记录
                             event_type = role_grant_idp / role_revoke_idp
                             user_id = NULL（系统操作，无人工 actor）
  7. 提交                    db.commit()
  8. 缓存失效                invalidate_effective_roles_cache(redis, user_id)
                             使变更在用户的下一个请求立即生效


4.3 三向集合 diff
----------------------------------------------------------------
  情况                          条件                         动作
  ----------------------------- ---------------------------- ----------------
  IdP 有，DB 没有              role_id ∈ idp_roles           INSERT UserRole
                               ∉ existing_idp_grants         source_ref='idp:<group>'
                                                             写审计 role_grant_idp

  DB 有，IdP 没有              role_id ∈ existing_idp_grants  UPDATE status='revoked'
                               ∉ idp_roles                   写审计 role_revoke_idp

  两边都有                     role_id ∈ 两者交集            不做任何操作


4.4 不受 reconcile 影响的角色
----------------------------------------------------------------
reconcile 的查询条件是 source='permanent' AND source_ref LIKE 'idp:%'。
以下角色完全不受影响：

  来源             source        source_ref        说明
  ---------------- ------------- ----------------- -----------------------
  直接分配          permanent     NULL              seed_data.py 创建的
                                                  或管理员通过 admin API
                                                  直接授予的永久角色
  项目角色          project       <project_id>      加入项目自动授予
                                                  (role_admin.py)
  临时角色          temporary     <工单号/审批号>    用户申请+管理员审批
                                                  (role_requests.py)

这意味着 IdP 只管它自己来源的角色，不会误删管理员手动分配的权限。


================================================================
五、source_ref 约定
================================================================
user_roles 表的 source_ref 字段是角色来源的溯源标识。
IdP 来源的角色使用 'idp:<group_name>' 格式：

  source_ref 值                  含义
  ------------------------------ ----------------------------------
  idp:aspire-compliance-team     IdP 组 aspire-compliance-team 授予
  idp:aspire-all-employees       IdP 组 aspire-all-employees 授予
  idp:aspire-platform-ops        IdP 组 aspire-platform-ops 授予

其他来源的 source_ref 约定：
  NULL                           直接分配（seed 或 admin 手动授予）
  <project_id>                   项目角色（如 proj_aml_upgrade）
  <工单号>                        临时角色审批单号


================================================================
六、审计日志
================================================================
IdP 驱动的角色变更写入审计哈希链，与其他审计记录一样防篡改。

  字段            IdP 记录的值
  --------------- ------------------------------------------------
  event_type      role_grant_idp（新增）或 role_revoke_idp（撤销）
  user_id         NULL（系统操作，无人工 actor）
  decision        allow
  deny_reason     idp_group:<group_name>（新增时）
                  或 idp_group_removed:idp:<group_name>（撤销时）
  filter_applied  {"target_user_id": "<uuid>", "role_id": "<role_id>"}

查询 IdP 相关审计记录（需要 platform_admin 或 auditor 身份）：
  GET /api/admin/audit?keyword=role_grant_idp
  GET /api/admin/audit?keyword=role_revoke_idp

通过 MCP 审计接口查询：
  search_audit_logs(keyword="role_grant_idp")


================================================================
七、管理后台视图
================================================================
管理员在 /admin/roles 页面查看用户角色时，每个角色授予行显示
source 和 source_ref 字段（UserRoleOut schema）。
IdP 来源的角色会显示：
  source: permanent
  source_ref: idp:aspire-compliance-team

这使得管理员可以直观区分角色来源：
  source_ref = NULL              → 直接分配
  source_ref = idp:...           → IdP 来源
  source = project               → 项目角色
  source = temporary             → 临时角色

API 查询某用户的所有角色授予（含来源）：
  GET /api/admin/users/{user_id}/roles
  返回 UserRoleOut 列表，每条含 source, source_ref, status。

八、演示场景
================================================================

8.1 场景 A：IdP 组变更导致角色撤销
----------------------------------------------------------------
演示 IdP 作为角色权威来源的效果：

1. 用 alice 登录（她有 aspire-compliance-team 组）
   → 登录后 alice 有 compliance_officer 角色

2. 模拟 IdP 侧移除 alice 的 compliance 组：
   编辑 group_mapping.py 中 MOCK_IDP_USERS["alice"] 的 groups，
   去掉 "aspire-compliance-team"

3. alice 再次登录
   → compliance_officer 的 IdP 授予行变为 status='revoked'
   → alice 不再有 compliance_officer 角色
   → 审计日志新增一条 role_revoke_idp 记录

4. 查看审计：
   GET /api/admin/audit?keyword=role_revoke_idp
   可看到系统撤销记录，user_id=NULL 表示 IdP 驱动


8.2 场景 B：新用户 JIT provisioning
----------------------------------------------------------------
演示从未登录过的用户首次登录时自动创建：

1. 在 MOCK_IDP_USERS 中添加一个新用户：
   "newemployee": {
       "groups": ["aspire-all-employees", "aspire-finance-traders"],
       "email": "newemployee@aspire.demo",
       "department": "Finance"
   }

2. 该用户不在数据库 users 表中

3. 用 newemployee 登录
   → 系统自动创建 User 行（clearance=1, compartments=[]）
   → 授予 employee + finance_analyst 角色（source_ref='idp:...'）
   → 登录成功，可使用系统

4. 管理员查看：
   GET /api/admin/users 可看到新用户
   GET /api/admin/users/{user_id}/roles 可看到 IdP 来源的角色授予


8.3 场景 C：IdP 角色与管理员直接分配共存
----------------------------------------------------------------
演示多来源角色叠加：

1. 管理员通过 admin API 直接给 alice 授予一个角色：
   POST /api/admin/roles/grant
   {"user_id": "<alice_id>", "role_id": "risk_analyst",
    "source": "permanent", "source_ref": null}

2. alice 登录（IdP reconcile 运行）
   → IdP 来源的 employee + compliance_officer 正常 reconcile
   → 管理员直接分配的 risk_analyst (source_ref=NULL) 不受影响

3. 查看 alice 的角色列表：
   GET /api/admin/users/{alice_id}/roles
   → 三行：employee (idp:aspire-all-employees),
          compliance_officer (idp:aspire-compliance-team),
          risk_analyst (NULL)
   → effective_roles = {employee, compliance_officer, risk_analyst}

九、运维操作
================================================================

9.1 切换 IdP 适配器
----------------------------------------------------------------
修改 .env 中的 IDP_PROVIDER 后重启后端：

  IDP_PROVIDER=mock      # 当前可用
  IDP_PROVIDER=oidc      # 预留，当前会抛 NotImplementedError
  IDP_PROVIDER=saml      # 预留，当前会抛 NotImplementedError

重启命令：
  docker compose restart backend


9.2 更新 group → role 映射
----------------------------------------------------------------
方法一：修改 group_mapping.py 中的 DEFAULT_GROUP_ROLE_MAP（需要重启）

方法二：创建 JSON 映射文件并配置路径（不需要改代码）
  echo '{
    "aspire-all-employees": "employee",
    "aspire-finance-traders": "finance_analyst"
  }' > /data/idp_group_role_map.json

  在 .env 中设置：
  IDP_GROUP_ROLE_MAP_PATH=/data/idp_group_role_map.json

  重启后端生效。

注意：映射在每次登录时从文件重新读取（load_group_role_map），但
get_idp_adapter() 被 @lru_cache 缓存，只创建一次适配器实例。
MockIdPAdapter 在每次 authenticate() 调用时读取 MOCK_IDP_USERS，
不读取映射文件——映射文件由 idp_reconcile.py 的 load_group_role_map()
读取。


9.3 添加新演示用户到 Mock IdP
----------------------------------------------------------------
编辑 group_mapping.py 的 MOCK_IDP_USERS，添加一行：

  "newuser": {
      "groups": ["aspire-all-employees", "aspire-compliance-team"],
      "email": "newuser@aspire.demo",
      "department": "Compliance"
  },

同时确保 seed_data.py 中有对应的 User 行（可选——如果没有，
JIT provisioning 会在首次登录时自动创建）。

修改后重启后端生效：
  docker compose restart backend


9.4 手动触发角色缓存失效
----------------------------------------------------------------
正常情况下不需要手动操作——登录时的 reconcile 会自动调用
invalidate_effective_roles_cache()。

如果需要手动清某用户的缓存（例如直接改了数据库）：

  docker compose exec redis redis-cli DEL "effective_roles:<user_uuid>"

或清所有用户的缓存：

  docker compose exec redis redis-cli --scan --pattern "effective_roles:*" | \
    xargs docker compose exec redis redis-cli DEL


9.5 排查登录失败
----------------------------------------------------------------
  症状                       可能原因                   排查方法
  -------------------------- -------------------------- --------------------------
  401 "账号不存在"           IdP 不认识该用户           检查 MOCK_IDP_USERS 中
                                                        是否有该 username
  500 NotImplementedError    IDP_PROVIDER 设为 oidc     改回 mock 或实现
                            或 saml（未实现）           对应适配器
  登录成功但角色不正确       group→role 映射缺失        检查 DEFAULT_GROUP_ROLE_MAP
                            或组名拼写不一致            或映射文件中是否有该组
  登录成功但角色未更新       Redis 缓存未失效           检查 Redis 是否可达，
                            （30 秒 TTL）               或手动清除缓存
  新用户登录后 clearance=1   JIT provisioning 默认      这是设计行为。
                            clearance=1                 clearance 需由 HRIS
                                                        来源设定（buddy.txt P1）


9.6 查看某用户的角色来源
----------------------------------------------------------------
  # 通过 admin API（需要 platform_admin 身份）
  GET /api/admin/users/{user_id}/roles

  # 直接查数据库
  docker compose exec postgres psql -U rbac -d rbac_rag -c \
    "SELECT role_id, source, source_ref, status
     FROM user_roles
     WHERE user_id = '<uuid>'
     ORDER BY created_at DESC;"

  # 只看 IdP 来源的角色
  docker compose exec postgres psql -U rbac -d rbac_rag -c \
    "SELECT role_id, source_ref, status
     FROM user_roles
     WHERE source_ref LIKE 'idp:%'
     ORDER BY status, role_id;"


================================================================
十、扩展指南：接入真实 OIDC / SAML IdP
================================================================

10.1 实现新适配器
----------------------------------------------------------------
1. 创建新文件，例如 app/services/idp/oidc_idp.py：

   from app.services.idp.base import IdPAuthenticationError, IdPUserInfo

   class OIDCIdPAdapter:
       def authenticate(self, auth_code: str) -> IdPUserInfo:
           # 1. 用 auth_code 换 access_token + id_token
           # 2. 解码 id_token 获取 sub (username), email, groups claim
           # 3. 返回 IdPUserInfo(username, email, department, idp_groups)
           #    认证失败 raise IdPAuthenticationError
           ...

2. 在 factory.py 中注册：

   if settings.idp_provider == "oidc":
       from app.services.idp.oidc_idp import OIDCIdPAdapter
       return OIDCIdPAdapter()

3. 在 config.py 中添加 OIDC 相关配置：

   oidc_client_id: str = ""
   oidc_client_secret: str = ""
   oidc_discovery_url: str = ""
   oidc_redirect_uri: str = ""

4. 修改 auth.py 的 login 端点以接收 OIDC 回调
   （auth_code 而非 username）。

适配器只需要实现一个方法：
  def authenticate(self, ...) -> IdPUserInfo

返回的 IdPUserInfo.idp_groups 列表会被 map_groups_to_roles() 映射，
后续的 reconcile 逻辑完全复用，无需改动。


10.2 OIDC/SAML 对接要点
----------------------------------------------------------------
  项目                OIDC                        SAML
  ------------------- --------------------------- ---------------------------
  认证流程            Authorization Code Flow     SP-initiated SSO
  用户标识            id_token 的 sub claim       SAML Assertion 的 NameID
  组信息来源          id_token 的 groups claim    SAML AttributeStatement
                      或 /userinfo 端点           中的 groups Attribute
  映射配置            IDP_GROUP_ROLE_MAP_PATH     同左
                      指向 JSON 文件               指向 JSON 文件
  JIT provisioning    同现有逻辑（IdP 返回的用户   同左
                      在 DB 不存在则自动创建）
  reconcile           完全复用现有逻辑             完全复用现有逻辑


10.3 注意事项
----------------------------------------------------------------
- clearance 和 compartment 不是 IdP 来源的。IdP 只管 role。
  clearance 来自 HRIS（buddy.txt P1），compartment 来自 LDAP/AD（P2）。
  JIT provisioning 创建的新用户 clearance=1, compartments=[]，
  需要等 HRIS/LDAP 同步或管理员手动设置后才有完整权限。

- 真实 OIDC/SAML 登录需要 HTTPS（回调端点必须安全）。
  当前 mock 模式不需要。

- get_idp_adapter() 使用 @lru_cache，适配器实例只创建一次。
  MockIdPAdapter 在每次 authenticate() 时读取 MOCK_IDP_USERS（不缓存），
  真实适配器如果需要 token 缓存/刷新，需在适配器内部处理。

================================================================
十二、常见问题
================================================================

Q: 登录后用户角色比以前多了一个 employee，是 bug 吗？
A: 不是。这是正确行为。IdP 返回的 aspire-all-employees 组映射为
   employee 角色，reconcile 会授予它。之前 seed_data.py 直接分配的
   employee 角色 (source_ref=NULL) 仍然存在，两者共存但
   get_effective_roles 返回 set（去重），所以有效角色不变。
   如果 seed 没有给某个用户分配 employee，登录后会多出来。

Q: 如果 IdP 和管理员都授予了同一个角色，会怎样？
A: 会有两行 user_roles：
   - source_ref=NULL (管理员直接分配, status='active')
   - source_ref='idp:...' (IdP 来源, status='active')
   get_effective_roles 返回 set，去重后只算一个。不影响功能。
   如果管理员撤销了直接分配的那行，IdP 来源的那行仍然有效。

Q: 临时角色到期后会怎样？
A: get_effective_roles 在查询时实时判断 end_at > now，
   到期的临时角色不计入有效角色集。不需要后台任务。
   但 user_roles 行不会被自动删除或改状态——它留在表中，
   只是查询时被排除。审计完整性不受影响。

Q: 能同时用多个 IdP 吗？
A: 当前设计是一次只用一个 IdP（由 IDP_PROVIDER 决定）。
   如果需要多 IdP，可以在适配器内部做路由（按邮箱域名分发到不同 IdP），
   reconcile 逻辑不需要改。

Q: reconcile 失败了怎么办？
A: 如果 IdP 不可达，authenticate() 抛 IdPAuthenticationError，
   登录端点返回 401。用户无法登录，但数据库中的现有角色不受影响
   （reconcile 在 IdP 认证通过后才开始改数据库）。
   如果数据库提交失败，整个事务回滚，不会出现部分写入。

Q: 可以关闭 IdP reconcile 吗？
A: 当前没有开关。每次登录都会走 reconcile。如果需要关闭，
   可以在 auth.py 的 login 端点中跳过 reconcile_user_with_idp()，
   改为直接查 User 表（即回到之前的"模拟 SSO"行为）。
