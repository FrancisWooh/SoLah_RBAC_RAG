风险提示（更新）：排查过能不能用本地 Postgres 替代验证 TencentVectorDBStore
——不行，tcvectordb 是私有RPC协议，Postgres 不是协议兼容的替身。但发现一个
更好的办法：tcvectordb 这个包本身已经装在镜像里，其中 Document/Filter 这
两个类是纯本地的数据/字符串构造类，不发网络请求，可以直接用真实SDK代码
测试——已加 test_tencent_adapter.py（5个用例全过），验证了请求构造
（Filter表达式、Document字段映射）和响应解析逻辑是对的。
真正没法在没有真实密钥情况下验证的，只剩：client鉴权 + create_collection
+ upsert/search 的实际RPC调用这几步，上线前仍需用真实密钥跑一次
seed_vectorstore.py 冒烟测试。
顺带发现 Tencent 的 Filter 语法（In/NotIn/Include/Exclude/IncludeAll）
和 Qdrant 一样，也没有"真子集"或"字段为空"的原生表达能力，所以 Tencent
路径的 compartments 校验完全交给 Python 层 is_permitted()，不在DB层做
近似预过滤（比 Qdrant 版本更保守，但更不容易踩坑）。

发现并修复了一个真实bug（不是我编的，是手工curl冒烟测试测出来的）：
场景二一开始测出来是错的——alice查"客户投诉处理SOP"（她没有customer_support
角色）本应被拒绝，但系统返回了allow，把KYC/CASA文档（她确实有权限看）当成
答案引用了。根本原因：RBAC过滤后拿到的"允许访问的top-k"不代表"真的相关"——
向量检索总会返回permitted集合里最接近的k个，哪怕分数很低也会返回。
修复：加了相关性阈值过滤，只有分数达标的permitted结果才真正用来回答；
分数不达标时，用一个"permission-blind"的peek_top_score()（只看分数，
不返回doc_id/内容）判断"是不是有更相关但被权限挡住的内容"，来决定
audit里标 deny 还是"确实没有相关内容"。threshold=0.20 是针对
MockEmbedder在这4篇种子文档上的实测分数分布校准的，换成真实hunyuan
embedding后必须重新测一遍分数分布，这个阈值大概率不适用。

中途修了一个测试基础设施的bug（不是这次新写的功能本身的bug，是M3/M4期间
就存在、这次才暴露出来的）：tests/conftest.py 的 db_session fixture一直
没有真正隔离——它只是手动开了个连接层事务，但没用SAVEPOINT，所以只要
被测代码自己调用了 db.commit()（M4的查询接口、这次M5的grant/revoke/
join/leave全都会commit），那次commit会直接穿透到真实数据库，测试
"结束时rollback"根本没用，等于每跑一次测试就会往真实表里permanent写
脏数据。已验证：M4那次测试运行确实往audit_logs表泄漏了1条真实记录
（manual curl一条+测试泄漏一条，一共2条，数字对得上）。修复方式是
Session加 join_transaction_mode="create_savepoint" 参数（SQLAlchemy 2.0
官方推荐的测试事务隔离写法）。修复后重跑全部36个测试，确认不再泄漏。
那条历史遗留的脏数据留着没删（反正是无害的审计记录，删了反而不像真实
使用痕迹）。

1. 测试基础设施：新加的 test_audit.py 一跑就非预期失败，查出来是

   没传值时，哈希是在插入前算的（这时候字段是None），但SQLAlchemy的列

   历史记录是用backfill脚本读"实际落库后的值"算的哈希，没受影响，没有
   脏数据需要清。
2.（M5遗留，这次顺带复查）确认了之前对 tests/conftest.py 的
   create_savepoint 修复是有效的——这次新写的 grant/revoke/export
   相关测试都会真实调用 db.commit()，全部验证过跑完之后真实表没有
   新增脏数据。

这次又抓到两个测试基础设施坑（都是真测出来的，不是编的）：
1. 我手工smoke测试时真的给bob批准了一个card_ops临时角色（为了验证
   真实流程），这条真实数据后来导致两个新写的pytest用例"预期deny"
   实际收到"allow"——因为真实数据库里bob确实有效拥有这个角色。
   不是代码bug，是我自己的手工测试数据忘记清理了，用revoke接口
   清理后（没有直接删库，走的是正常撤销流程，保留了可追溯的审计
   记录）恢复正常。
2. 真正的基础设施bug：Redis的effective_roles缓存不在pytest的数据库
   事务回滚范围内——A测试grant了角色、紧接着查询了一次（缓存里写入
   了"有这个角色"，TTL30秒），B测试虽然数据库状态被正确回滚了，但
   如果在30秒内跑，会命中A测试留下的stale缓存，导致B测试跟着错。
   在conftest.py加了个autouse fixture，每个测试开始前清空
   effective_roles:*这些缓存key，解决。
这两个坑背后是同一类问题：业务逻辑横跨两个存储（Postgres+Redis），
测试只隔离了其中一个，就会被另一个的真实/残留状态悄悄污染。

M10　（原"审计自然语言问答"）改成：本地只读 MCP server — 已完成
====================================================================
原计划是我们自己在Dashboard里做一个问答框，LLM把问题转成SQL查询再总结
回答。讨论后改变方向，原因：
1. 没有真实Hunyuan密钥，LLM那层的"智能"在Mock模式下做不出真实价值；
2. 查过WorkBuddy官方文档，它没有"发个请求过去拿一段文字回答"那种
   inbound API——它是桌面应用，连接器是反过来的（WorkBuddy主动连外部
   服务），但它支持接自定义MCP server（stdio和HTTP都支持，文档确认过）。
所以改成：把审计/角色申请相关的只读查询能力做成MCP工具，让WorkBuddy
自己来做"查alice过去7天被拒绝的查询->判断是否在反复试探财务文档->
顺便列出她的角色申请记录"这种多步编排——这正是agent该干的事，不用
我们自己手搓一套不成熟的NL->SQL逻辑。只做只读，不做写操作（grant/
revoke/approve/reject 一律不开放给MCP，这是明确决定，不是漏做）。

[x] 加 `mcp` 官方SDK依赖，新建 app/mcp_server.py，用FastMCP注册7个只读

    get_audit_log_detail / verify_audit_chain / list_role_requests /
    get_dashboard_stats——全部复用已有的service层函数，没有重新写一遍
    查询逻辑
[x] 鉴权：每个工具调用都要求 Authorization: Bearer <JWT>，走的是和REST
    接口一样的 decode_access_token + effective_roles 检查platform_admin，
    只是换成了MCP的Context机制（ctx.request_context.request）去拿

    request确实是真实的Starlette Request（不是瞎猜的）

这次又顺带修了一个之前就埋下但还没暴露的测试基础设施坑：
加了 app.mount("/mcp", ...) 之后，7个旧测试文件全挂了——
RuntimeError: StreamableHTTPSessionManager .run() can only be called once
per instance。原因是每个测试文件都各自 `with TestClient(app) as c`，
每次都会完整地重启一遍app的lifespan，而FastMCP的session manager只能
被真正"进入"一次。改成全部测试文件共享conftest.py里一个
session级别的TestClient（这其实也是更标准的pytest写法，之前每个测试
都重启一遍app本来就没必要）。改完确认：连续跑3遍suite，66个测试全过，
没有不稳定，audit_logs表行数也没有因为跑测试而增长。

解析工具调用报错、怎么把配置的凭证塞进请求头——这需要真实WorkBuddy
实例才能确认，我们这里没有。正式接入前建议先用WorkBuddy实际连一下
这个MCP server冒烟测试。
